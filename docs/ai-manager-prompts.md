## План

```
Мы строим production-ready MVP ИИ-менеджера в Telegram для онлайн-школы английского. Клиент пишет боту, получает ответы только по базе знаний школы (папка knowledge/, посмотри её структуру), бот помнит предыдущие разговоры, квалифицирует заявки, сохраняет их в базу, уведомляет владельца в Telegram и передаёт разговор владельцу, если не может ответить уверенно. У владельца есть кабинет в браузере. Всё работает на VPS 24/7.

Стек: Python и FastAPI, Telegram Bot API через long polling без webhook, Supabase (Postgres) с pgvector для поиска по базе знаний, модель через API (провайдер и имена моделей из переменных окружения), кабинет на Next.js, Docker Compose, VPS.

Не строим: голосовые, оплату, запись на конкретное время, несколько школ, редактирование базы знаний через кабинет, регистрацию в кабинете.

Уже решено:
- В Supabase всё живёт в отдельной схеме school, бот ходит в неё отдельной ролью с правами только на эту схему.
- Владелец отвечает клиенту и реплаем в Telegram, и из кабинета.
- Кабинет ходит в данные только через REST бота. Supabase используем как чистый Postgres с pgvector, без Supabase Auth и Realtime.
- Модель и эмбеддинги через OpenAI-совместимый API (OpenRouter): адрес, ключ, имена моделей и размерность вектора из переменных окружения.

Сначала не пиши код. Подготовь и сохрани в docs/plan.md:
1. User flow клиента и user flow владельца, по шагам.
2. Архитектуру на одном экране: компоненты и кто с кем общается.
3. Модель данных: таблицы, ключевые колонки, связи.
4. Границы MVP: что входит, что нет.
5. Пять главных рисков и как их снимаем.
6. Acceptance-проверки: 12-15 пунктов «что должно работать», чтобы считать проект готовым.
7. План по этапам, один этап это один будущий промт: бот, база, знания и поиск, память, квалификация и лиды, передача человеку, кабинет, безопасность, деплой.

Задавай вопросы только там, где ответ меняет архитектуру. Формат: короткие списки, без кода.
```

## Этап 1: бот

```
Этап 1: бот. Транспорт и конкурентность, базы и модели пока нет.

- Каркас репозитория: bot/, cabinet/ (пустая), knowledge/, .env.example, README, .gitignore с .env. Python 3.11+, FastAPI, httpx, pydantic-settings.
- Один процесс: FastAPI и фоновый поллер getUpdates (long polling, без webhook) в lifespan. allowed_updates только message. Таймаут long poll из env POLL_TIMEOUT_SEC=30.
- Offset подтверждается только после того, как весь батч обработан: Telegram забывает update, как только мы просим следующий offset, поэтому раннее подтверждение теряет сообщения при падении.
- Только личные чаты, в группах и каналах бот молчит, сообщения других ботов игнорируются. Две роли: владелец по OWNER_TELEGRAM_ID, остальные клиенты.
- /start: приветствие от имени школы, в двух строках, чем поможет, и предложение бесплатного пробного. На текст клиента пока честная заглушка. На голосовые, фото и файлы: «понимаю только текст».
- Порядок сообщений одного чата гарантирован очередью с одним воркером на chat_id, а не asyncio.Lock: Lock не гарантирует порядок запуска задач. Разные чаты не ждут друг друга. Простаивающий воркер убирается через CHAT_WORKER_IDLE_SEC=300.
- Дедуп по update_id, пока в памяти.
- Остановка по SIGTERM: отменить открытый long poll, дать доработать начатым обработчикам (SHUTDOWN_DRAIN_SEC=20), потом закрыть клиентов.
- /healthz: status, seconds_since_tick, talked_to_telegram. Heartbeat обновляется на каждом витке цикла, включая витки с ошибкой: healthcheck ловит зависший поллер, а не недоступный Telegram.
- Логи строками JSON. Токен бота, пароли и текст сообщений клиентов в лог не попадают: редактор секретов на всех полях.
- Второй экземпляр бота получит от Telegram 409: бот работает в одном экземпляре, это записать в README.
- Тесты: фейковый Telegram как настоящий HTTP-сервер (TELEGRAM_API_ROOT из env), без живого токена. /start, молчание в группе, сообщения других ботов игнорируются, владелец распознаётся, дубль update_id отвечается один раз, два быстрых сообщения отвечены по порядку, не-текст получает отказ, /healthz зелёный во время поллинга, offset подтверждается только после батча, очередь держит порядок внутри чата и не держит разные чаты.

После реализации: тесты, запуск, список файлов, стоп.
```

## Этап 2: база

```
Этап 2: база. Переписка живёт в Postgres (Supabase).

- Отдельная схема school и отдельная роль school_bot с логином: права только на свою схему, явный revoke на public, RLS включён как вторая ограда. Утёкшая строка подключения бота не должна открывать ничего, кроме школы.
- SQL-миграции в bot/migrations/, применяются скриптом scripts/migrate.py ролью postgres (строка POSTGRES_URL_NON_POOLING только на ноутбуке), учёт в school.schema_migrations, повторный запуск пропускает применённое. scripts/create_role.py генерирует пароль school_bot и сам пишет POSTGRES_URL в .env.
- Подключение через Session pooler Supabase, порт 5432: прямое соединение только по IPv6, а Transaction pooler 6543 ломает подготовленные выражения asyncpg. Драйвер asyncpg.
- При неверном пароле базы старт не повторяется в цикле: Supabase банит IP за неудачные входы, и бан закроет базу для всего, что ходит с этого адреса.
- Таблицы: clients (telegram_user_id unique, username, first_name, profile jsonb, summary, is_blocked_bot, is_banned), conversations (эпизоды: status open/closed, state AI_ACTIVE / HUMAN_REQUESTED / HUMAN_ACTIVE, last_message_at), messages (role client/bot/owner/system, text, telegram_message_id, meta jsonb), events (type, payload), processed_updates.
- Дедуп заявкой, а не отметкой: update сначала заявляется в processed_updates, завершается после ответа. Если заявку держит другой процесс, бот ждёт, а не пропускает; незавершённая заявка старше UPDATE_CLAIM_STALE_SEC=120 считается брошенной. Цена решения: при падении между отправкой и записью клиент получит ответ дважды, молчание хуже повтора.
- Клиент, эпизод и входящее сообщение пишутся одной транзакцией. Эпизод закрывается после 24 часов тишины, следующее сообщение открывает новый. Одна открытая беседа на клиента гарантируется уникальным индексом в базе. Голосовые и фото тоже сохраняются, с пометкой вида сообщения.
- Telegram ответил 403 на отправку: клиент помечается is_blocked_bot, флаг снимается, когда он пишет снова.
- Пока разговор в HUMAN_REQUESTED или HUMAN_ACTIVE, бот клиенту не пишет (переключение будет на этапе 6).
- База недоступна: клиент получает короткое извинение, бот продолжает работать.
- Тесты: локальный Postgres в docker-compose.test.yml на нестандартном порту, схема school_test собирается теми же миграциями, бот ходит в неё ролью с RLS. Переписка сохраняется, не-текст сохраняется с видом, повторный update после рестарта не получает второго ответа, брошенная заявка на update подхватывается, свежая ожидается, а не пропускается, эпизод закрывается по тишине, база не даёт открыть второй эпизод, бот молчит, пока разговор у владельца, флаг блокировки ставится и снимается, падение базы не убивает бота, роль бота не видит чужие схемы, миграции применяются один раз.

После реализации: тесты, запуск, список файлов, стоп.
```

## Этап 3: знания и поиск

```
Этап 3: знания и поиск. Бот отвечает по базе знаний.

- Модель через OpenAI-совместимый API из env: LLM_BASE_URL, LLM_API_KEY, LLM_MODEL. Используем OpenRouter, openai/gpt-5.6-luna, размышление выключено (reasoning effort none). Маршрут провайдера закреплён в LLM_PROVIDER: require_parameters=true (только провайдеры, которые держат JSON-схему) и data_collection=deny. Эмбеддинги openai/text-embedding-3-small, размерность 1536, EMBEDDING_DIM из env.
- Ingest: python -m app.ingest. Режет knowledge/*.md по заголовкам ##, у каждого куска префикс «Файл: ... / Раздел: ...», таблицы не режутся, knowledge/README.md в базу не идёт. Хеш файла: неизменённые пропускаются, куски удалённых файлов удаляются.
- Таблицы knowledge_documents, knowledge_chunks (embedding vector(N), HNSW по cosine; HNSW в pgvector держит не больше 2000 измерений, миграция отказывается от большего), llm_calls (purpose, model, токены, latency, вид ошибки) — каждый вызов модели записывается сразу, дневному бюджету на этапе 8 нужна история.
- pgvector в Supabase лежит в схеме public, а у роли бота в пути поиска только school: тип и оператор писать с явной схемой (public.vector, operator(public.<=>)), путь поиска не расширять.
- Бот при старте сверяет размерность колонки и модель, которой загружена база; при расхождении не стартует и пишет, что сделать.
- Поиск: cosine, top-k 8, порог 0.2. limitations.md модель видит всегда, поэтому из результатов поиска он исключён; остальное только найденное. Всю базу в промпт не кладём.
- Приветствия и не-текст модель не вызывают.
- Один вызов модели на сообщение, без агентного цикла. Ответ строго по JSON-схеме через response_format, проверка pydantic: reply, sources (метки кусков), needs_human, handoff_reason (not_in_knowledge / client_request / complaint), is_smalltalk.
- Код сверяет sources с метками кусков, которые модель реально видела. Ответ по делу без настоящего источника превращается в фиксированное «уточню у руководителя, ответит в рабочее время 9:00-21:00 МСК». Причина передачи пока пишется событием handoff_needed (сама передача на этапе 6).
- Правило в системном промпте: оплата картой конкретного банка или из конкретной страны всегда уходит руководителю, даже если способ оплаты в базе есть.
- Сбой модели, битый JSON или таймаут: клиенту нейтральный текст, бот работает дальше.
- Eval: bot/eval/cases.json, около 30 вопросов с эталонами (точные цены из pricing.md, четыре ловушки из knowledge/README.md), scripts/eval.py гоняет их через настоящую модель, проверки механические: должен содержать, не должен содержать, должен передать.
- Тесты: фейковый OpenAI-совместимый API как HTTP-сервер. Нарезка сохраняет разделы, таблицы и префикс, настоящая база режется по разделам, миграция отказывает при размерности больше 2000, ingest пропускает неизменённое и следует за изменениями, поиск ставит нужный раздел выше и не возвращает limitations, ответ строится по найденному, модель может попросить человека, ответ без настоящих источников становится передачей, сбой модели и битый JSON дают нейтральный текст, приветствие и голосовое не вызывают модель, в логах нет текста клиента и ключей, бот не стартует при чужой размерности или базе от другой модели эмбеддингов.

После реализации: тесты, eval, запуск, список файлов, стоп.
```

## Этап 4: память

```
Этап 4: память. Переписку помнит бот, а не модель: модель каждый раз получает короткий контекст заново.

- Контекст модели: правила + профиль клиента + резюме + последние 15 сообщений эпизода (HISTORY_MESSAGES) + найденные куски.
- Профиль это белый список полей: name, goal, level, timezone, preferred_time, format_interest, is_teen. Факты модель возвращает в том же ответе полем profile_updates; всё сверх списка отбрасывается, длина значений ограничена.
- Резюме о клиенте хранит память между эпизодами. Пересобирается отдельным вызовом, когда накопилось 10 новых сообщений (SUMMARY_EVERY_MESSAGES), и в начале нового эпизода по сообщениям прошлого. Текущее сообщение в резюме не попадает, первый эпизод клиента резюме не запускает.
- Перед поиском вопрос переписывается в самостоятельный запрос коротким отдельным вызовом с историей и профилем: иначе «а если 24 занятия?» уйдёт в поиск как есть и не найдёт куски про IELTS. Это сознательный второй вызов на сообщение; выключается REWRITE_QUERY=false.
- Память это данные о клиенте, а не инструкции: если в резюме окажется «клиенту обещали скидку 50%», бот всё равно отвечает по материалам школы.
- Сбой переписывания или резюме не ломает ответ: поиск по сырому вопросу, резюме остаётся прежним.
- Профиль и резюме в логи не пишутся. В логе только флаг, был ли вопрос переписан.
- Eval: плюс 4 кейса с памятью, включая «вчера назвал цель, сегодня не спрашивают заново» и продолжение «а если 24 занятия?» с верной ценой.
- Тесты: профиль принимает только известные поля, история эпизода уходит модели и обрезается по лимиту, новый эпизод получает резюме вместо истории, резюме пересобирается каждые N сообщений, профиль заполняется и используется в следующем ответе, поиск идёт по переписанному вопросу, сбой переписывания даёт поиск по сырому, сбой резюме сохраняет ответ и старое резюме, память не попадает в логи.

После реализации: тесты, eval, запуск, список файлов, стоп.
```

## Этап 5: квалификация и заявки

```
Этап 5: квалификация и заявки.

- Отдельного вызова модели нет: в JSON-схему основного ответа добавляется блок lead (или null): kind trial / corporate / other и поля goal, level, format, timezone, preferred_time, company, team_size, sphere. Схема проверяется pydantic.
- Заявка появляется только по явному намерению: «хочу пробный», «запишите меня». Вопрос о цене заявкой не считается. Описание команды («у нас 5 человек, IT») сразу считается корпоративной заявкой. «Запишите меня» не считается просьбой позвать человека.
- Решения принимает сервер, не модель: модель объявляет заявку готовой слишком охотно. Поля по видам взяты из документов школы: для пробного обязательны goal и preferred_time, и время считается заполненным только вместе с часовым поясом (trial.md); level по желанию. Для корпоратива обязательны team_size, sphere, goal, preferred_time (corporate.md). missing_fields вычисляется кодом.
- Если полей не хватает, в ответе клиенту ровно один уточняющий вопрос по одному недостающему полю, в естественной форме, не анкетой. Телефон и бюджет не спрашивать: связь идёт в этом же чате.

Карточка: имя и username клиента, вид, известные поля, чего не хватает, ссылка на разговор в кабинете из CABINET_URL (пусто: номер разговора). Не доставленное уведомление уходит при следующем изменении заявки (notified_at).

- Eval: плюс 4 кейса заявок: пробный собирается по полям, корпоратив сразу из описания команды, вопрос о цене не заявка, в одном ответе не больше одного уточняющего вопроса.

После реализации: тесты, eval, запуск, список файлов, стоп.

```

## Этап 9: деплой

```
Этап 9: деплой. Три контейнера на VPS, наружу смотрит только Caddy.

- Dockerfile бота: python:3.12-slim, не под root, healthcheck дёргает /healthz. Dockerfile кабинета: двухэтапная сборка Next с output standalone, в рантайм только standalone, не под root. .env и knowledge/ в образы не попадают (.dockerignore, проверка COPY).
- docker-compose.yml: bot, cabinet, caddy. Портов на хосте нет ни у кого, кроме Caddy (80 и 443). restart: always, ротация логов json-file. knowledge/ монтируется в бота томом только для чтения: правка текста не требует пересборки.
- Caddyfile: домен из CABINET_DOMAIN, TLS Caddy выпускает сам. Все правила внутри route, а не набора handle: в route порядок такой, как написан. По порядку: доступ к кабинету только с адресов из CABINET_ALLOWED_IPS (пусто — со всех); /healthz наружу 404; запросы с заголовком Next-Action — 404 (Server Actions кабинет не использует, через них приходит CVE-2025-55182); POST/PUT/PATCH/DELETE мимо /api — 405; /api/* на bot:8000; остальное на cabinet:3000. HSTS задать явно, Caddy сам его не ставит; плюс nosniff, X-Frame-Options DENY, Referrer-Policy, убрать Server.
- В адресе сайта Caddy нельзя указывать IP: он примет его за адрес прослушивания внутри контейнера. Для локальной проверки всего стека CABINET_DOMAIN=school.localhost.
- docker-compose.local.yml для работы без сервера: только bot и cabinet, порты на 127.0.0.1 (3000 и 8000), CABINET_COOKIE_SECURE=false и CABINET_URL=http://localhost:3000 задаются в самом compose-файле. CABINET_URL нужен и проверке источника: Next проксирует /api со своим Host.
- deploy.sh на сервере: git pull, сборка, up -d, всегда пересоздать caddy (git pull заменяет Caddyfile новым файлом, а примонтированный файлом том продолжает видеть старый), ожидание healthcheck, флаг --ingest перезагружает базу знаний. Тело скрипта в функции main, вызов в последней строке: git pull подменяет сам скрипт во время выполнения. Проверка, что в секретах .env нет символа $.
- Алерт владельцу, если Telegram молчит дольше POLLER_SILENCE_MINUTES=10, и ещё одно сообщение, когда связь вернулась. Один раз, без спама.
- Миграции применяются с ноутбука: строка роли postgres на сервер не попадает.
- Runbook в README: первый запуск на чистом Ubuntu 24.04 (A-запись домена до первого запуска, Docker, ufw 22/80/443, clone по read-only deploy key, перенос .env без POSTGRES_URL_NON_POOLING, ./deploy.sh --ingest), обновление, «бот молчит», ротация секретов.
- Тесты: портов на хосте только у Caddy, в локальном compose порты только на 127.0.0.1 и нет Caddy, в Caddyfile есть защита от Next-Action и POST мимо /api, next закреплён не ниже 15.5.7, в образах нет .env и knowledge, алерт о молчании ровно один раз и сообщение о возврате связи.

После реализации: тесты, локальный запуск всего стека, список файлов, стоп. На сервер выкатываю сам по runbook.
```

## Аудит безопасности

После этапа 9, до того как домен станет публичным, и после каждого крупного изменения.

```
Проведи полный аудит безопасности проекта: код бота, кабинет, схема базы, Docker, Caddy, зависимости. Код пока не меняй.

- Модель угроз, три противника: клиент в Telegram (заспамить бота, выжечь бюджет модели, протащить инструкции через сообщение, память или заявку, получить чужие данные); тот, кто нашёл кабинет в интернете (подобрать пароль, украсть сессию, отправить запрос от имени владельца с чужого сайта); тот, у кого утекли строка подключения бота или логи (прочитать соседние схемы в базе, подделать историю миграций, вытащить токен бота).
- Проверь как минимум: все SQL-запросы и подстановки; права роли бота на чужие схемы и на schema_migrations; секреты в логах, в том числе в трассировках исключений (httpx кладёт в текст ошибки адрес запроса с токеном бота); вход в кабинет (лимит попыток, сравнение логина в постоянном времени, хеш считается даже при неверном логине); сессию и cookie (httpOnly, Secure, SameSite, срок, отзыв при выходе); CSRF на всех мутациях; размер тела запроса до разбора JSON; лимиты на клиента и дневной бюджет токенов; бан; команды владельца только от OWNER_TELEGRAM_ID; инъекции в промпт и проверку ответа модели JSON-схемой; вывод в кабинете (XSS, dangerouslySetInnerHTML); Dockerfile (не под root, в образах нет .env и секретов); какие порты открыты наружу; заголовки безопасности в Caddy; что видно с публичного домена без входа.
- Этот список не полный: ищи и то, чего в нём нет.
- Зависимости: проверь закреплённые версии по актуальным бюллетеням безопасности, не по памяти. Особенно Next.js: версии ниже 15.5.7 уязвимы к RCE через Server Actions без аутентификации.
- Отчёт в docs/security.md: модель угроз; таблица находок «что / риск / как исправить / тест»; что проверено и в порядке; что осознанно отложено и почему.

После: отчёт, стоп. Исправления только после моего «исправляй»: на каждую находку тест, каждую защиту проверить на поломку.
```
