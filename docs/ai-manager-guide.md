# ИИ-менеджер в Telegram: как собрать с Claude Code

По этим промтам собирается Telegram-бот, который работает менеджером онлайн-школы английского языка. Он:

- отвечает клиентам строго по базе знаний школы;
- помнит клиента между разговорами;
- собирает заявки на пробный урок и корпоративное обучение;
- передаёт владельцу вопросы, на которые не знает ответа.

У владельца есть кабинет в браузере. В конце всё уезжает на сервер с доменом и HTTPS.

Промты описывают проект, который реально собран и работает, вместе с решениями, принятыми по ходу сборки.

Комплект из двух файлов:

- `ai-manager-prompts.md` — сами промты, в порядке отправки;
- этот файл — порядок работы, что понадобится, образец `CLAUDE.md` и итоговая проверка.

## Как пользоваться

1. Создайте пустую папку проекта и запустите в ней Claude Code.
2. Отправьте по порядку промты «База знаний», «План» и «CLAUDE.md».
   - План Claude сохранит в `docs/plan.md`. Прочитайте его и поправьте, если что-то не так: все этапы опираются на этот план.
   - `CLAUDE.md` можно сверить с образцом ниже.
3. Этапы 1–9 по одному. Отправили промт, дождались тестов и списка файлов, проверили руками, только потом следующий этап.
4. Перед этапом 7 сгенерируйте макет кабинета промтом «Дизайн кабинета» в ChatGPT и приложите картинку к промту этапа 7.
5. После этапа 9, до публикации домена, отправьте промт «Аудит безопасности».

Если хотите сначала понять, что будет строиться, напишите перед промтом этапа «опиши этап, ничего не делай». Когда всё понятно, пишите «приступай».

Модель соберёт не байт в байт то же самое, это нормально. Главное, чтобы проходили проверки, перечисленные в конце каждого этапа.

## Что понадобится

- **Бот:** токен от @BotFather и ваш Telegram ID, его можно узнать у @userinfobot.
- **Второй аккаунт Telegram.** Владелец в чате с ботом всегда остаётся владельцем, поэтому клиента удобнее играть со второго аккаунта.
- **База:** проект в Supabase, бесплатного тарифа хватит. Нужна строка подключения Session pooler, порт 5432.
- **Модель:** ключ OpenRouter. Весь путь от первого этапа до девятого обошёлся примерно в 20 центов.
- **Инструменты на компьютере:** Docker для тестовой базы, Python 3.11 или новее, Node.js 20 или новее.
- **Для этапа 9:** VPS с Ubuntu 24.04 и домен.

## Образец CLAUDE.md

Примерно такой файл должен получиться после промта «CLAUDE.md»:

```markdown
# ИИ-менеджер школы английского в Telegram

Бот отвечает клиентам школы Bridge English строго по базе знаний из `knowledge/`,
помнит клиента между разговорами, квалифицирует заявки и передаёт разговор
владельцу, когда не уверен. У владельца кабинет в браузере.

## Стек (не менять без запроса)

Python и FastAPI, один процесс: long polling Telegram Bot API без webhook плюс
REST для кабинета. Postgres с pgvector (Supabase), схема `school`, роль `school_bot`.
Модель через OpenAI-совместимый API, провайдер и имена моделей из env.
Кабинет на Next.js. Caddy, Docker Compose, VPS.

## Структура

    bot/app/         FastAPI, поллер, обработчики, адаптеры модели, поиск
    bot/tests/       тесты по этапам, фейковый Telegram вместо живого
    bot/migrations/  SQL-миграции схемы school
    cabinet/         Next.js, ходит только в /api бота
    knowledge/       база знаний школы, режется по заголовкам ##
    docs/plan.md     план и принятые решения

## Модель данных

clients, conversations, messages, leads, events, knowledge_documents,
knowledge_chunks, llm_calls, processed_updates, owner_sessions. Колонки и связи
в docs/plan.md.

## Состояния разговора

`AI_ACTIVE`: отвечает модель. `HUMAN_REQUESTED`: вопрос передан владельцу, он
ещё не подключился; бот продолжает отвечать на другие вопросы и пересылает
владельцу и вопрос, и свой ответ. `HUMAN_ACTIVE`: владелец ответил и ведёт
разговор сам, бот клиенту не пишет и только пересылает. Переданный вопрос
остаётся за владельцем в обоих случаях.

## Не строим в MVP

Голосовые, фото и файлы. Оплату. Запись на конкретное время. Несколько школ.
Редактирование базы знаний через кабинет. Регистрацию в кабинете. Рассылки.
Работу в группах и каналах. Realtime и аналитику в кабинете.

## Правила работы

- Один запрос это один этап. Ничего сверх запрошенного. Вижу лишнее, называю
  одной строкой и жду решения.
- После этапа: прогнать тесты, запустить приложение, перечислить изменённые
  файлы, остановиться.
- Каждую защиту проверяю на поломку: ломаю код, убеждаюсь, что тест падает,
  возвращаю.
- Секреты только в `.env`. В репозитории только `.env.example`. Содержимое
  `.env` не вывожу никогда, ни в ответ, ни в лог.
- Не выдумываю методы Telegram Bot API, их параметры и возможности Supabase.
  Не уверен, читаю документацию или спрашиваю.
- Модель получает только текущий разговор, профиль текущего клиента и найденные
  куски знаний. Всю базу в промпт не кладу.
- Ошибка внешнего API не роняет бота: ловим, пишем в лог, клиенту нейтральный
  текст и передача владельцу.
- В логах нет текста сообщений клиентов, только id, тип события, длительность.
- Все суммы в долларах, язык ответов клиенту русский.
- Решения, принятые по ходу, записываю в docs/plan.md с причиной.
- Коммит после каждого изменения; коммит, закрывающий этап, называется
  `step-N-название`.
```

## Дизайн кабинета

Три совета, чтобы результат не разочаровал:

- **Генерируйте по одному экрану.** Если попросить три экрана на одной картинке, текст расплывётся, а сетка поедет. Для экранов заявок и входа переиспользуйте дословно блоки «Типографика», «Цвет», «Геометрия» и «Чего не должно быть»: так экраны получатся одной системой.
- **Кириллицу модель всё равно частично исказит.** Картинка задаёт композицию, плотность и тон, а точные подписи берутся из кода.
- **Палитра и шрифт здесь — просто минималистичный вариант.** Если у школы свой цвет, меняйте блок «Цвет», остальное от этого не пострадает.

## Зачем аудит до публикации

Этап 8 начинается с аудита. Этот промт — повторный аудит: после этапа 9 до того, как домен станет публичным, и потом после каждого крупного изменения. Свежий домен сканеры находят за минуты: каждое новое имя видно в публичных логах сертификатов, и по нему сразу идут эксплойты вроде CVE-2025-55182 для Next.js. Поэтому аудит нужен до публикации, а не после.

## Что проверить в конце

- Новый клиент пишет /start и получает приветствие и предложение пробного.
- «Сколько стоит 16 занятий с носителем?»: точная цена из pricing.md и название раздела.
- «Готовите к TOEFL?»: честное «нет, только IELTS» без передачи владельцу.
- «Есть скидка для студентов?»: «нет», никаких выдуманных акций.
- «Можно оплатить картой Kaspi?»: «уточню у руководителя», у владельца карточка.
- Владелец отвечает реплаем, клиент получает ответ, разговор виден в кабинете.
- Клиент называет цель, через день спрашивает «какой курс мне подойдёт»: цель учтена, заново не спрашивают.
- «У нас команда 5 человек, IT»: корпоративная заявка, у владельца карточка.
- 30 сообщений за минуту: одна вежливая пауза, владелец не заспамлен.
- Кабинет: без входа 401, неверный пароль отклонён, 10 неверных подряд блокируют вход.
